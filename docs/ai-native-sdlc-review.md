# The AI-Native SDLC Playbook — 검토 요약과 Orbit 적용안

출처: https://claude.com/blog/the-ai-native-sdlc-playbook (Anthropic, Applied AI 팀). 검토일 2026-09-05.

## 1. 글의 핵심 주장

"코드 작성은 더 이상 병목이 아니다." 전통 SDLC 는 코딩이 가장 오래 걸리던 시절에 맞춰 설계됐는데, 에이전트가 구현을 시간 단위로 끝내면서 병목이 양쪽으로 이동했다 — 왼쪽(계획·요구사항·설계)과 오른쪽(테스트·검토·배포)은 여전히 사람 속도이고, "사람이 코드 한 줄씩 검토하던" 통제 방식은 생산량을 따라갈 수 없다. 규제 조직은 "검토 큐가 쌓이거나, 덜 검토된 코드가 나가거나" 둘 다 받아들일 수 없으므로 **프로세스 자체를 바꿔야** 한다.

해법은 SDLC 를 선형(단계별 핸드오프)에서 **순환(각 단계가 다음 단계가 읽을 산출물을 커밋)** 으로 바꾸는 것. 산출물 체인이 곧 감사 흔적이다:

| 단계 | 산출물 | 사람이 개입하는 지점 |
|---|---|---|
| Plan | `intent.md` (발의자의 말로 쓴 의도) | 제품 담당자 승인 |
| Design | `spec.md` (조직 정책 = Skills 를 제약으로 적용) | 정책 담당자와 concern 협의 |
| Build | `plan.md` + 코드 + 테스트 (plan mode 로 계획 먼저) | 엔지니어가 계획 승인 |
| Test | 테스트 출력·스크린샷·eval 결과 | 없음 — 기계적 증거가 리뷰어 역할 |
| Deploy | PR + 검토 발견 (`REVIEW.md`) | 코드 오너 승인, 프로덕션 게이트 |
| Maintain | 인시던트 기록 → 다시 `intent.md` | 온콜이 분류 |

원칙 한 줄: **"사람의 판단은 루프 위에 있고, 루프는 계속 돈다."**

## 2. 단계별 요점

**Plan** — 아이디어를 가진 사람이 엔지니어를 기다리지 않고 Claude 와 대화해 `intent.md`(문제·제안 결과·영향 범위·제약·열린 질문)를 직접 커밋한다. 지표: 첫 대화→커밋까지 시간(주 단위→시간 단위), 스펙 확정 이후 intent 가 바뀐 횟수.

**Design** — 요구사항과 설계를 한 세션으로 합친다. 브랜드·보안·규정준수 정책을 **Skill**(트리거 조건 + 절차가 든 마크다운)로 코드화해 스펙을 쓰는 순간 적용한다. Skill 은 "권고적"이므로 반드시 지켜야 하는 정책은 뒤에 **Hook**(결정적: 허용/차단/승인 요청)을 둔다.

**Build** — plan mode(읽기 전용)로 `plan.md`(바꿀 파일·순서·위험·증명 방법)를 먼저 만들고 승인받은 뒤 구현한다. `CLAUDE.md` 는 "신입이 첫날 알아야 할 것"(명령어·규약·아키텍처·**Claude 가 자주 틀리는 것**)을 담는 제도적 지식 파일. 보호 경로 편집 차단, 포맷터 자동 실행, 비밀값 차단은 Hook 으로. 독립 작업은 git worktree 로 병렬 세션.

**Test** — 모든 세션은 사람이 보기 전에 스스로 검증한다: `make test` 같은 단일 진입점, 정량 목표("4개 상태 테스트 통과", "스크린샷이 목업과 일치"), 버그는 실패 테스트부터, "테스트 통과 전엔 완료가 아님"을 CLAUDE.md 에 선언, 수정 중 테스트 파일 편집은 Hook 으로 금지. 그리고 **연속 eval**: 최근 실제 작업 20~50개를 프롬프트+합격 기준으로 만들어 CLAUDE.md/Skill/Hook 이 바뀔 때마다 CI 에서 돌린다. 프로덕션 인시던트는 그 팀이 eval 로 바꿔 영구 회귀 테스트로.

**Deploy** — 검토는 양방향: Claude 가 `REVIEW.md`(버그/보안/규정준수 세 패스, Important 와 Nit 의 정의, PR 당 nit 5개 캡, 제외 목록)대로 검토하고, `@claude` 로 코멘트 반영도 한다. 발견은 merge 를 막지 않고 정보만 제공, 승인은 branch protection 의 사람 몫. 같은 실수가 두 번 나오면 CLAUDE.md 에 추가. Hook 은 "물어보기"까지 확장되어 변경관리 사인오프·릴리스 인증이 게이트가 되고, 조직 필수 Hook 은 관리 설정으로 개인이 우회 못 하게. CI 에서는 읽기 전용 판단(빌드 실패 분류)부터 시작해 쓰기 단계(lint 수정, 문서 갱신)를 게이트 뒤에 붙이고, 배포는 MCP 툴로 노출하되 환경별 자율성(개발 자유 → 프로덕션은 준비까지만). 롤백은 가장 자주 리허설하는 경로.

**Maintain** — 결정적 스크립트가 프로덕션 지표를 관제 밴드(롤링 기준선 ± σ, Western Electric 규칙)로 감시하고, 1σ 는 로그, 2σ 는 Claude 가 읽기 전용 진단, 3σ 는 PR 열기 또는 사전 승인된 런북 실행. 진단 결과는 `intent.md` 로 파이프라인에 재진입한다. 정기 보안 스캔(Claude Security)과 채널 온콜(Claude Tag: Slack 에서 첫 응답자, 채널 자체가 감사 기록)도 같은 원리 — 사람이 호출 경로에 없어도 루프가 돌고, 결과물은 항상 PR 검토 게이트를 통과한다.

## 3. 횡단 개념

- **거버넌스 4층**: Skill(권고) → Hook(결정) → 권한/샌드박스(OS) → branch protection + 사람 승인. 민감한 정책은 중앙 관리 설정, 팀 워크플로는 `.claude/` 폴더에서 git 리뷰.
- **레거시 공존**: Jira/ServiceNow 가 진실이면 마크다운은 작업 사본(MCP 로 왕복), 아니면 repo 중심. 어느 쪽이 진실인지 먼저 정한다.
- **관측**: 모든 실행이 OpenTelemetry 로 나가고(프롬프트·툴 호출·Hook 결정·에이전트 ID), 대시보드 지표는 첫 검토까지 시간, eval 통과율, 게이트별 차단/허용 비율, 알림→진단 intent 까지 시간.
- **적용 순서**: 단계는 의존 그래프라 Build 부터 하려면 Design→Plan 이 먼저 필요하지만, 조직이 Hook·승인 게이트부터 강제하고 팀이 Skill·CLAUDE.md 를 채우는 순서도 가능.

## 4. Orbit 과의 대응 — 이미 있는 것

| 플레이북 | Orbit 현재 구현 | 비고 |
|---|---|---|
| `intent.md` → `spec.md` → `plan.md` 체인 | 목표 → `/api/projects/:id/plan` 제안 → 카드+하위 작업(apply) | 제안을 사람이 검토·수정한 뒤 apply 하는 2단계가 "plan mode 승인"과 같은 구조 |
| `CLAUDE.md` (제도적 지식) | 선언적 기억(user/project/agent 스코프) + 리뷰 패스 | "Claude 가 자주 틀리는 것" 섹션에 해당하는 것이 agent 스코프 노트 |
| Skills | `skills` 테이블 + `use_skill`/`save_skill` (인덱스만 주입, 본문은 요청 시) | 플레이북의 Skill 은 정책, Orbit 의 스킬은 절차 — 정책용 스킬(scope=global)로도 쓸 수 있음 |
| Hook (결정적 게이트) | 서킷브레이커(연속 3회 → 409), 회상 상한, 기억 project 스코프 승인 대기, 위협 스캔 | 전부 "차단" 형이고 "물어보기" 형은 없음 |
| REVIEW.md / 양방향 검토 | 없음 — 검토 열은 사람이 봄 | 아래 5절 1번 |
| 검증을 완료의 일부로 | `complete_task` 필수 호출, blocked 사유 | "증명(proof)" 항목은 없음 |
| 연속 eval | 없음 | 5절 2번 |
| 관제 밴드 → intent 재진입 | 없음 (사용량 대시보드만) | 5절 4번 |
| 채널 온콜 | 카드 댓글이 사람↔에이전트 채널 | 댓글 = 채널 히스토리 = 감사 기록, 같은 원리 |
| 산출물 체인 = 감사 흔적 | agent_runs.metadata + task_comments + recall_docs | 커밋 체인 대신 DB 행이지만 역할은 같음 |

## 5. Orbit 에 가져올 만한 것 (우선순위 순)

1. **검토 에이전트와 `REVIEW.md`** — 검토 열에 올라온 카드를 다른 에이전트(Lint)가 "버그/정책 준수/스펙 일치" 세 패스로 검토해 Important/Nit 을 구분한 댓글을 남기고, 사람은 그것을 보고 승인만 한다. 프로젝트별 `review` 스킬을 정책 파일로 쓰면 기반이 이미 있다. 서킷브레이커처럼 "검토 발견은 막지 않고 정보만" 원칙을 지킬 것.
2. **연속 eval** — 실제 실행 20~30건을 프롬프트+합격 기준(complete_task 호출, 회상 ≤3, 기억 오염 없음, 요약에 근거 인용)으로 저장해 프롬프트·스킬·기억 규칙이 바뀔 때 돌린다. 이번 세션에서 겪은 "잘린 실행에서 리뷰 모델이 지어낸 기억" 같은 사고가 바로 eval 후보다.
3. **`complete_task` 에 `proof` 필드** — "무엇으로 검증했는지"(테스트 출력, 참조 링크, 확인한 파일)를 구조화해 받고, 없으면 검토 열 대신 대기로. 플레이북의 "완료 전 증거 첨부"를 가장 싸게 옮기는 방법.
4. **관제 밴드 → 카드 자동 생성** — 사용량·실패율·서킷브레이커 발동 횟수를 롤링 기준선과 비교해 2σ 면 Project Lead 가 진단 카드(`intent` 역할)를 대기 열에 만든다. 기존 planner 와 run-loop 로 구현 가능.
5. **"물어보기" 형 Hook** — 지금은 차단만 있는데, 예를 들어 에이전트가 create_task 로 카드를 5개 넘게 만들거나 global 스킬을 갱신하려 할 때 사람 승인 대기 상태로 두는 게이트. 기억의 pending 승인과 같은 패턴을 재사용.
6. **Hook 결정 로그** — 서킷브레이커·회상 상한·위협 스캔이 "언제 무엇을 막았는지"를 usage_events 처럼 남겨 대시보드에 "게이트별 차단 비율"을 보여 준다.

## 6. 유의할 점

플레이북은 엔터프라이즈(규제·감사) 조직을 전제로 하고 git·CI 가 진실의 원천이다. Orbit 은 D1 이 진실이고 사용자는 개인이라, "관리 설정 vs 팀 설정" 같은 계층은 지금 필요 없다. 반대로 플레이북에 없고 Orbit 에 있는 것 — 대화 압축, 에피소드 회상, 에이전트별 스코프 기억 — 은 Hermes 쪽 강점이니 그대로 유지하면 된다.
