# 실행·승인·과금 심층 분석

작성: 2026-09-06 KST. 코드 기준: c9a7fa7, main 병합: cd57a86.

## 후속 개선 — 2026-09-06

아래 여섯 발견 사항을 우선순위대로 수정했다. 이후 본문의 재현과 줄 번호는 수정 전 분석 기록이다.

| 우선순위 | 개선 결과 |
|---|---|
| P1 승인 경쟁 | pending 조건, 스킬·카드 생성, 승인 상태와 게이트 기록을 하나의 D1 트랜잭션으로 처리한다. 실패하면 모두 롤백되어 재시도할 수 있다. |
| P1 크레딧 분할 | 무료 잔액을 먼저 차감하고 초과분만 유료로 정산한다. |
| P1 중복 실행·잔액 경쟁 | 업무별 실행 토큰과 5분 임대, 30초 갱신으로 이전 실행의 늦은 결과를 차단한다. 모델 호출은 사용자별 예약으로 보호하며 같은 핸들의 후속 검토는 순서대로 처리한다. |
| P1 결제·환불 복구 | confirming/refund_pending 상태, 공급자 조회, 멱등 키, 결제 원장 고유 인덱스와 원자적 정산을 적용했다. 내역의 ‘처리 결과 확인’으로 재시도한다. 확정 환불 거절은 공급자 DONE 확인 후 예약을 해제하고, 모호한 결과는 보류한다. |
| P2 도구 오류 | 일반·스트리밍 모두 error 또는 ok:false를 실패로 기록한다. 승인 대기는 성공적인 보류로 유지한다. |
| P2 불완전 실행 | 완료 보고가 없는 종료는 차단 사유와 함께 보류한다. 자동 결과·기억 리뷰도 생략한다. 유효한 완료 보고가 있다면 마지막 응답의 토큰 중단만으로 완료를 취소하지 않는다. |

환불 확인 중인 충전도 실제 환불 완료까지 월 한도에 포함한다. 공급자 오류 분류는 [토스 공식 오류 코드](https://docs.tosspayments.com/reference/error-codes)를 기준으로 제한적으로 적용했다.

운영 특성: 서로 다른 요청의 크레딧 호출이 겹치면 409로 재시도를 안내한다. 한 호출의 실제 비용이 잔액을 넘을 수는 있으며 다음 호출을 중단한다. 공급자 응답 유실 시 알 수 없는 AI 사용량까지 복원하는 것은 이 변경의 범위에 포함되지 않는다. 결과가 불명확한 환불은 사용자 확인 재시도 전까지 크레딧 사용을 보류한다.

마이그레이션 0022는 트랜잭션 조건 검사, 실행 임대, 결제 원장 중복 방지를 추가한다. 기존 중복 원장이 있으면 고유 인덱스 생성이 실패하므로 운영 적용 전 중복 그룹 수를 확인한다. 과거 원장을 자동 삭제하지 않는다.

검증: lint·빌드, 회귀 테스트 77개 통과. 빈 DB에 마이그레이션 23개 적용 통과, 운영 중복 원장 0그룹 확인 후 0022 적용 완료. 실제 AI 전체 평가는 9/10 통과하고 승인 게이트가 HTTP 503으로 끝났으나, 최종 빌드에서 해당 케이스를 재실행해 통과했다(카드 3개, 승인 대기 3건). 최초 503의 원인은 응답에 오류 상세가 없어 확정하지 않았다. 스킬 출력의 내부 용어 경고 1건, 백그라운드 리뷰의 토큰 상한 및 평가 프로젝트 정리 후 외래키 오류 로그는 별도 후속 관찰 항목으로 남긴다. 결제 실패·복구 검증은 공급자 응답을 모사한 로컬 테스트이며 운영 실결제를 수행하지 않았다.

- 승인 범위 필수화, 표시 이름에 따른 승인 우회 제거, 평가 기록 보강, 린트 정리를 PR #1로 병합했다.
- Cloudflare Worker `orbit` 버전: `3060dd85-ff73-48f2-91aa-b1cdd3b3098b`.
- lint, 단위 테스트 47개, 빌드 통과. 임시 DB 마이그레이션 22개 통과, 원격 DB 미적용 0개.
- 실제 AI 승인 평가: 카드 3개 생성, 카드 2개와 전역 스킬 1개 승인 대기.
- 운영 HTTP 확인: 랜딩·로그인·약관·개인정보 페이지 200, www 308, 미로그인 앱 307, 보호 API 401, 인증 제공자 API 200.
- 운영 사용자 계정으로 로그인하거나 실제 결제·에이전트 실행을 시도하지 않았다. 아래 재현은 임시 로컬 SQLite/Vitest 환경이며 운영 데이터는 변경하지 않았다.

## 1. P1 — 거절 이후에도 늦은 승인이 실행될 수 있다

근거: `lib/approvals.ts:59`, `:68`, `:74`.

승인 처리는 pending 조회 → 실제 부작용 실행 → 상태 UPDATE로 분리되어 있다. 마지막 UPDATE에는 pending 조건이 없고, 작업도 상태 전이와 같은 원자적 처리에 묶이지 않는다.

**로컬 재현 확인:** 승인 요청이 pending을 읽은 시점에서 중지하고 거절 요청을 완료했다. DB 상태 rejected, 스킬 0개를 확인한 뒤 승인을 재개하면 승인도 성공하고 상태 approved, 전역 스킬 1개가 된다. 승인 두 번이 겹치면 카드 생성에 각기 다른 UUID를 써 중복 생성될 가능성도 있다(이 변형은 정적 확인).

수정 방향: 승인 ID별 조건부 상태 전이, 부작용과 상태의 원자적 반영, 부작용 식별자의 멱등성을 함께 설계한다. 상태 UPDATE에 조건만 추가하고 카드 생성은 앞에 두면 해결되지 않는다. 실패 복구와 재시도도 필요하다.

필수 테스트: 동시 승인 두 번, 승인/거절 교차, 작업 중 DB 실패, 같은 요청 재시도.

## 2. P1 — 무료·유료 크레딧 경계 차감이 잘못된다

근거: `lib/credits.ts:196-201`.

누적 사용량이 무료 잔액을 넘으면 해당 호출 비용 전체를 유료 버킷에 기록한다. 무료 잔액과 초과분을 나누지 않는다.

**정적 계산 확인:** 무료 100, 유료 1,000 밀리크레딧에서 비용 150인 호출은 무료 100 + 유료 50을 차감해야 한다. 현재 로직은 유료 150만 차감해 무료 100, 유료 850이 남는다. 총잔액은 맞지만 유료 잔액과 환불 가능 판단이 잘못된다. 무료 크레딧만 있을 때는 무료 잔액을 남겨둔 채 유료 버킷이 음수가 될 수도 있다.

수정 방향: 호출 직전 남은 무료 잔액과 이번 비용을 비교해 무료·유료 차감 행을 분할하고 한 배치로 반영한다. 요청 사이 동시성도 별도로 다뤄야 한다.

필수 테스트: 무료 잔액보다 작은/같은/큰 비용, 무료만 보유한 초과 호출, 연속 호출, 환불 가능 잔액 계산.

## 3. P1 — 동일 업무와 잔액을 여러 실행이 동시에 사용할 수 있다

근거: `lib/run-task.ts:239-245`, `:372`; `lib/credits.ts:185-193`.

업무 실행 시작 시 새 agent_runs를 무조건 추가하며 진행 상태에 대한 조건부 점유가 없다. 늦게 끝난 요청도 업무 결과를 무조건 덮어쓴다. 별도의 과금 핸들은 각자 같은 잔액 스냅샷을 읽으므로 beforeCall 검사만으로 요청 간 중복 소비를 막지 못한다. credit_holds 테이블은 잔액 계산에 읽히지만 현재 lib 코드에는 예약 생성 경로가 없다.

**정적 확인:** 두 탭, API 재시도, 매니저 위임과 직접 실행이 겹치면 AI 호출·후속 카드·비용이 중복될 수 있다. 운영에서 실제 발생했는지는 조사하지 않았다.

수정 방향: 업무별 실행 점유와 실행 토큰을 두고 완료 시 현재 토큰을 확인한다. 프로세스 종료 후 잠금 복구를 위한 만료/갱신도 필요하다. 잔액은 호출 전 원자적 예약, 호출 후 정산·반납으로 보호한다.

필수 테스트: 동일 업무 동시 실행, 서로 다른 업무의 잔액 경쟁, 중단 후 재실행, 이전 실행의 늦은 완료.

## 4. P2 — 업무 오류가 도구 성공으로 기록된다

근거: `lib/claude.ts:270-279`, 스트리밍 `:461-468`; `lib/run-task.ts`의 memoryWrites/skillsUsed 집계.

도구들은 검증 실패 시 `{ error: ... }`를 반환한다. 호출 래퍼는 throw만 오류로 판단한다.

**로컬 재현 확인:** executeTool이 `{ error: 'denied' }`를 반환했는데 trace.ok가 true였고, 다음 모델 요청의 tool_result에는 is_error가 없었다. 오류 본문은 전달되므로 모델이 본문을 읽고 복구할 가능성은 있지만, 프로토콜 상태와 지표는 잘못된다.

수정 방향: 도구 반환 규약을 정하고 일반·스트리밍 루프에서 동일하게 해석한다. 승인 대기는 오류가 아닌 정상 보류이므로 오류와 구분해야 한다.

필수 테스트: 반환 오류, throw, 정상 성공, 승인 대기, 일반/스트리밍의 일치.

## 5. P2 — 완료 보고 없이 중단된 실행이 completed로 남는다

근거: `lib/run-task.ts:323-343`, `:366-394`.

blocked 여부를 complete_task 보고에만 의존한다. 보고가 없으면 false가 되어 크레딧 부족·반복 상한·토큰 상한 중단도 completed, 업무 검토 상태로 저장될 수 있다. 출력에는 중단 문구가 있어도 상태와 집계는 완료를 나타낸다. 자동 검토도 이어져 추가 호출을 시도한다.

**정적 확인:** 실제로 complete_task를 호출한 뒤 마지막 문장만 토큰 한도에 걸린 경우는 별도로 취급해야 한다. 종료 이유만 보고 무조건 실패로 바꾸는 것도 부정확하다.

수정 방향: 유효한 완료 보고의 존재, 중단 시점, stopReason을 함께 보고 완료/차단/불완전을 판정한다. 불완전 실행에서는 자동 후속 호출을 제어한다.

필수 테스트: 보고 전 잔액 부족, 보고 전 반복/토큰 상한, 보고 이후 마무리 중단, 정상 완료.

## 6. P1 — 결제 승인 오류의 상태 확정과 원장 멱등성이 부족하다

근거: `lib/payments.ts:174-203`; `drizzle/0021_credits.sql`.

토스 요청의 모든 예외를 payments.failed로 확정한다. 타임아웃은 외부 승인의 성공 여부가 불명확한데도 실패로 닫혀 이후 재시도가 order_closed로 거부될 수 있다. 동시에 들어온 요청의 오류 처리도 pending 조건 없이 성공 상태를 failed로 덮어쓸 수 있다.

성공 경로는 payments의 pending 조건부 UPDATE 다음에 원장 INSERT를 무조건 수행한다. 업데이트가 0행이어도 원장이 추가될 수 있고, 원장에는 결제별 charge 중복을 막는 고유 제약이 없다. **외부 제공자가 중복 요청에 어떻게 응답하는지는 이번 분석에서 검증하지 않았으며, 중복 지급의 실제 발생을 단정하지 않는다.** 내부 상태와 원장이 독립적으로 보호되지 않는 점은 코드에서 확인했다.

수정 방향: 외부 결과 불명확 상태와 확정 실패를 구분하고 조회·재조정 경로를 둔다. 결제별 멱등 키와 원장 고유 제약, 상태 전이와 지급의 원자성을 적용한다. 환불도 같은 기준으로 검토한다.

필수 테스트: 외부 성공 후 응답 유실, 중복 승인, 성공/오류 응답 순서 역전, 지급 전 DB 실패, 중복 환불.

## 권장 실행 순서

1. 승인 상태 전이와 과금 버킷 분할: 재현 또는 계산으로 확인됐고 사용자 승인·잔액에 직접 영향.
2. 결제 복구·멱등성과 업무 실행/잔액 예약: 재시도와 동시 요청을 안전하게 처리.
3. 도구 오류 규약과 완료 상태 판정: 실제 동작·사용자 표시·평가 지표를 일치시킴.

위 항목은 이번 배포로 새로 생긴 회귀가 아니라 기존 코드의 후속 수정 대상이다. 이번 분석에서는 제품 소스를 추가 수정하지 않았다.
